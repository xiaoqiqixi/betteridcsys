# 升级、数据库兼容与回滚

适用于本次维护候选版本；不提供自动部署、自动降级或不可逆数据库操作。升级前先完成独立恢复演练，见 [BACKUP_RECOVERY.md](BACKUP_RECOVERY.md)。保留源码提交、Linux 包与校验和、旧版本目录、配置版本、秘密引用和数据库备份时点。

## 数据变化

本轮保留迁移 1/2/3 的既有内容，使用迁移 2 保存站点设置和账单身份、迁移 3 建立双币种价格表，新增迁移 4 保存订单身份并约束服务币种与金额精度，迁移 5 为订单/账单/服务增加精确二进制币种约束（拒绝 usd 或带重音的近似拼写）。迁移文件嵌入二进制，以编号和 SHA-256 校验和记录在 `schema_migrations`；已经应用的迁移不能修改。迁移器校验完整前缀并拒绝超出本二进制理解范围的数据库版本。确切迁移清单以同一发布源码的 `backend/migrations/` 和验证记录为准。

- 站点设置是独立持久化记录，带 revision 乐观并发控制；管理员更新与审计在同一事务中提交。
- 新订单和账单保存创建时的金额、币种与开具身份；后续设置或价格变动不改历史记录。
- 迁移前的账单缺少历史开具身份时保持缺失，不把今天的公司资料补成过去的抬头。
- 原 USD 价格迁入 `plan_prices`；新增 CNY 示例价格保持不可售。既有 USD 的可售状态由迁移继承，不代表本次重新核准运营价格。逐项审核产品和币种后再启用。
- CNY 是默认选择项，不是汇率规则。不能将旧 USD 数字直接贴成 CNY，也不能把历史 USD 账单转换成 CNY。

MySQL DDL 存在隐式提交，无法靠外层事务把整个迁移自动回滚。迁移重复执行和已知中断点处理必须在隔离副本验证；不要把 `IF NOT EXISTS` 当作任意结构损坏的修复器。发现 checksum 不匹配或未知 schema 版本，应停止并审查原因，禁止手改 `schema_migrations` 绕过检查。

## 操作流程

1. 在隔离恢复库测试目标版本：升级迁移、重复迁移、就绪检查、旧账单读回、设置写入、新 CNY/USD 订单和权限负向测试。确认生产库身份、域名和端口不会被副本复用。
2. 宣布维护窗口并阻断新增业务写入。当前没有滚动升级兼容性保证；保持单版本 API，避免旧客户端/旧 API 与新库并行写入。保存旧版未完成订单及其原幂等键，不用新键盲目重试。
3. 完成最终备份与校验，记录数据时点。保留旧应用文件和依赖清单；归档不得含秘密。
4. 停止 API，用目标版本和独立迁移身份执行 `-migrate`。核对迁移输出、记录版本和校验和，运行身份继续保持 DML 权限。
5. 原生部署把 `/opt/aster/current` 原子切换到已经解压并核验的新目录；Compose 使用已核验镜像/源码，不用浮动标签猜测实际版本。启动 API，检查 `/readyz` 后再恢复网页与写入。
6. 验证两种语言独立切换、两种币种各自价格、历史账单身份/币种不变、管理员保存冲突提示、客户无权更新设置、禁用支付仍返回明确失败。检查日志与数据库错误率，完成观察窗口。

原生 symlink 切换示例（维护窗口中执行；目录已经创建并验证，VERSION 由管理员替换）：

```sh
sudo systemctl stop aster-api
# 先按安装手册执行新二进制 -migrate，成功后再切换。
sudo ln -s /opt/aster/releases/VERSION /opt/aster/current.next
sudo mv -T /opt/aster/current.next /opt/aster/current
sudo systemctl start aster-api
```

`current.next` 若已存在，应检查上次操作结果后处理，不用 `ln -sf` 隐藏未知状态。nginx 读取 `current/web`，API 与网页应在同一维护窗口切换；不要长期混用旧网页缓存和新接口。

## 失败后的判断

**迁移尚未开始、库未变更**：停止新版本，恢复旧目录/镜像与配置，验证旧应用就绪后再恢复写入。

**迁移已提交**：旧二进制可能因新 schema 版本而拒绝启动。本版本没有向下迁移；不能承诺只切换旧二进制即可回滚。优先保留现状、诊断并向前修复，或按审查过的恢复方案重建隔离库再切换。不要删除新字段、手改 checksum 或强行让旧代码忽略版本。

**必须恢复数据库**：先停写、保存失败现场和当前数据副本，确认备份时点及之后可能丢失的所有写入，再由负责人员批准切换。先在另一个数据库恢复，核验业务数据后更换 DSN。禁止直接把 SQL 导入运行库、`DROP DATABASE` 或 `docker compose down -v` 当作快捷回滚。

回滚结束也需要完整业务验收。记录失败原因、影响时段、选择的恢复点、数据差异及后续行动；不得把“进程启动”当作数据正确性结论。
